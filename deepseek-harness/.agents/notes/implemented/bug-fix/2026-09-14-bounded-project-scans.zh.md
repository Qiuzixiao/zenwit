# Agent Note：项目扫描有界化与结构重载合并

Status: implemented

[English](2026-09-14-bounded-project-scans.md) | 中文

## 问题

桌面端渲染进程耗尽 V8 堆后崩溃（`exitCode: 5`，上报为 `crashed`），发生在 `yarn dev` 启动几分钟之后；Crashpad 中自 2026-09-10 起有六个此类 minidump，每一个都记录了 out-of-memory 崩溃键。GC 日志直接点名了进程：存活 4,060 MB，堆上限 4,091.8 MB，每 1.5–2.5 ms 触发一次 Scavenge 却几乎回收不到任何对象——活动监视器里那 ~109% CPU 是垃圾回收，不是业务计算。崩溃分配点上抓到两个 JavaScript 栈：`ui-workbench` 包内 `flattenFiles` 之下的 `flatMap`，以及 shell 包 `subscribe` 之下的 `Set.add`。桌面端自带的恢复机制重载了三次页面，随后报出 "renderer recovery timed out waiting for page load and client health"——一个无法自愈的白屏窗口。

决定性的驱动因素是文件树渲染，而第一次修复并没有给它设界。`Workspace.tsx` 在文件搜索框有任何文字时把所有目录都视为展开（`isOpen = fileQuery.trim() !== '' || expanded.has(node.path)`），于是一个能匹配项目大部分内容的查询会在 render body 里为**每个节点**创建一个元素——本仓库为 19,350 个节点、约 12 万个 DOM 元素——而且每次渲染都如此。用一个 5,000 节点的项目加查询 `file` 做的探针，在 5 秒测试超时内**从未完成一次渲染**。文件变更流会持续推高 revision，于是每一遍在提交前就被重启：堆里塞满了无法提交的存活工作（mutator 占用 98%，Scavenge 回收不到任何东西），V8 在 4,093 MB 上限中的 2,875 MB 处中止。

先前那次扫描瘦身是必要的，但并不充分。Host 的结构扫描会遍历整个项目，包括 `node_modules`：本仓库根目录有 212,365 个文件，其中 191,713 个是依赖文件，而一次扫描返回 134,481 个节点（15,751 个目录、118,730 个文件）、23.5 MiB JSON，以及 2,393 ms 的同步工作，其中为打印字数而完整读取了 5,467 个 markdown 文件（47.4 MiB）。`GET /changes` 按文件系统批次逐个推送事件，Client 把每个事件都变成一次 `fileRevision` 自增，而每次自增都会重载整棵树。Client 还在每次渲染时重新拍平全部 118,730 个文件节点，并且过期响应在被陈旧性检查丢弃之前就已经解析成了完整对象图。`yarn dev` 本身就是触发器：它会向正在运行的应用所监听的同一个项目写入数千个文件。

## 决策

扫描有界，且永不进入依赖缓存。`zenwit-workspace/src/structure-scan.ts` 用显式的条目上限参数持有两条遍历路径——结构树与 `@` 资源；路由传入 `MAX_SCAN_ENTRIES`（50,000）并在响应中报告 `truncated`。`node_modules` 永不被进入，因为包缓存不是项目内容。同一个项目根现在以 19,350 个节点、约 0.3 s 完成扫描，节点 `detail` 契约未变——剩余时间中约三分之二是 markdown 字数统计。

两个被渲染的列表都有界。文件树把一份渲染预算（`TREE_RENDER_LIMIT`，400 行）贯穿整个递归，元素创建在预算处停止，而不是跟着匹配集合走，并在面板上说明只显示了前若干行；快速打开对话框最多渲染 `QUICK_OPEN_LIMIT`（100）行，且键盘导航索引的就是这份列表。`filterTree` 与快速打开的过滤都改为按各自输入派生，而不再每次渲染重算。

Client 不再为同一次扫描反复付出代价。`Workspace.tsx` 用 `useMemo` 以结构响应为键派生拍平后的文件列表，因此搜索输入不再重新遍历整棵树；它还在 `res.json()` 之前检查请求世代，取消未读取的响应体，而不是解析一棵不会被渲染的树。`index.ts` 把一串变更事件合并为每 250 ms 窗口至多一次 `fileRevision` 自增。该 revision 仍是一个数字，因此所有既有消费者——树重载、外部变更同步、编辑器对账——契约不变，只有速率改变。

`truncated` 在 `StructureResponse` 上是可选的，因此不做扫描上限的 Host 仍保持兼容。Client 会显示本地化提示，而不是暗示文件树是完整的。

消费者可见的变更：`node_modules` 不再出现在文件树或 `@` 引用选择器中。其中的文件仍可通过文件端点按路径读取。

## 考虑过的其他方案

**只限制事件速率，保留无界遍历。** 单次扫描本身就有 23.5 MiB 常驻渲染状态，而比本仓库更大的项目即使事件速率很低也仍会耗尽堆。

**加预算但不排除依赖缓存。** 一个对真实项目足够大的预算（本仓库排除 `node_modules` 后约需 20,000 个节点）会截断用户本可合法浏览的文件树。

**按目录惰性加载。** 这是长期正确的设计，但它会改变结构响应、树组件以及搜索与快速打开路径，而所报告的缺陷并不要求这一点。已作为延期工作在包 README 中记录。

**在 Host 侧缓存扫描结果。** 缓存能掩盖遍历开销，但掩盖不了 23.5 MiB 的响应，而且会在本就存在的变更流之上再加一层失效问题。

**在 `Workspace.tsx` 内做防抖，而不是在变更流入口。** 该 revision 同时驱动外部变更同步与编辑器对账；合并应发生在事件到达处，而不是某一个消费者处。

**延迟统计字数或干脆去掉。** 字数只占现存 275 ms 扫描中的 218 ms，因此要缩短的是遍历，而不是 detail 文本。
## 影响

单次扫描被限制在 50,000 个条目以内并跳过依赖缓存：本仓库根从 134,481 个节点 / 23.5 MiB / 2,393 ms 降到 19,350 个节点 / 3.3 MiB / 约 0.3 s。两个被渲染的列表分别限制在 400 行与 100 行，因此项目规模不再决定元素数量：先前在 5 秒超时内从未完成的 5,000 节点渲染探针，现在以最多 400 行在 507 ms 内完成。超出预算的项目会得到被截断的文件树与一条本地化提示，而不是渲染进程崩溃。`node_modules` 不再能在文件树或 `@` 选择器中浏览——这是排除策略的有意代价；其中的文件仍可通过路径读取。变更风暴现在每秒至多触发四次扫描，而不是每个变更文件一次，因此文件树最多会滞后一次构建 250 ms。

两部分改动一并发布：Client 能容忍不发送 `truncated` 的 Host，而 Host 从不发送 Client 必须理解的字段。验证由 `zenwit-workspace/tests/structure-scan.test.mjs`（缓存排除、预算恰好在边界处精确上报、保留的深度限制、未变的 markdown detail）、断言 `node_modules` 不出现在 `/structure` 与 `/resources` 的 Host HTTP 测试，以及覆盖截断提示、一次搜索驱动的重渲染中每棵树只拍平一次、被取消的过期响应、每串事件只自增一次 revision 的 Client 规格共同完成。
